# ネットワーク講座「電車アナロジー」リライト用定義ファイル（完全統合版）

既存のネットワーク講座テキストを「電車・鉄道網」のアナロジーに置き換えて書き直すための基本概念、用語対応表、およびリライトプロンプトである。

## 1. 全体コンセプトと世界観

*   **デバイス（スマホ/PC/サーバー/ルーター/プロキシ/LB等） ＝ すべて「駅（Station）」**
*   **MACアドレス ＝ 駅の「固定の駅名（物理的固有ネーム）」**（例：スマホ駅、お父さんPC駅、ルーター駅）
*   **IPアドレス ＝ そのまま「IPアドレス」と呼ぶ**（駅に割り振られる変動可能な管理番号・住所）
*   **データ / パケット ＝ 「乗客（または荷物を抱えた乗客）」**
*   **通信ネットワーク ＝ 「鉄道網（線路・改札・運行ルール）」**

## 2. 登場用語 vs 電車アナロジー 完全対応表

### 【デバイスと識別子（識別番号）】
* **デバイス（スマホ, PC, サーバーなど）** ＝ **駅**
* **MAC Address（MACアドレス）** ＝ **固定の駅名**（例: `AA:BB:CC:11:22:33` という改札口固有の不変の駅名）
* **IP Address（IPアドレス）** ＝ **そのまま「IPアドレス」と呼ぶ**（路線網で割り当てられる駅の番号/住所）
* **Local IP（プライベートIP）** ＝ **ローカル線（私鉄・家の中）の中だけで通用する「構内IPアドレス」**
* **Global IP（パブリックIP）** ＝ **全国ネット（JR・インターネット）で通用する「全国IPアドレス」**
* **Port Number（ポート番号）** ＝ **駅の中にある「特定のホーム番号・受取窓口」**（例: 443番ホーム＝Web受取窓口）

### 【通信の最小単位とネットワーク区分】
* **Packet（パケット）** ＝ **小分けにされて電車に乗る「乗客（荷物）」**
* **Internet（インターネット）** ＝ **世界中を繋ぐ「巨大な全国鉄道網（新幹線・幹線）」**
* **Subnet（サブネット）** ＝ **同じ鉄道会社・同じエリア内にある「同一路線グループ」**
* **CIDR（サイダー表記）** ＝ **「どこまでのIPアドレスが同じ路線グループ（サブネット）か」を示す路線エリアの境界線ルール**（例: `/24`）

### 【ネットワーク機器・接続技術】
* **Wi-Fi（ワイファイ）** ＝ **「見えない空中レール（無線の線路）」**（駅と駅をケーブルなしで繋ぐ）
* **L2 Switch（L2スイッチ）** ＝ **同じ路線エリア内（LAN）の駅同士を繋ぐ「構内線路切替ポイント（操車場）」**
* **Default Gateway（デフォルトゲートウェイ）** ＝ **「ほかの路線へ出るための乗り換え接続駅（ターミナル改札口）」**

### 【セキュリティ＆負荷分散（追加コンポーネント）】
* **Bastion Server（踏み台サーバー）** ＝ **「厳重なセキュリティチェックがある特別許可・乗り継ぎ専用駅（検問所駅）」**
  * *解説：* 外部から直接アクセスできない安全な秘密のエリア（社内LAN等）に入るために、一度だけ下車して身元確認（認証）を受けるためだけの専用駅。
* **Proxy Server（プロキシサーバー）** ＝ **「乗客の代わりに買い物やWeb閲覧に行ってくれる『代理購入窓口駅』」**
  * *解説：* スマホ駅（乗客）が直接目的地へ行くのではなく、一度代理駅（プロキシ）へ行き「代わりにあのサイトのデータを買ってきて！」と頼む。代理駅が代わりにアクセスして結果をスマホ駅へ届ける（身元隠蔽やキャッシュに利用）。
* **Load Balancer（ロードバランサー）** ＝ **「混雑を防ぐための『改札誘導・ホーム振り分け専門駅（交通整理ステーション）』」**
  * *解説：* 大量の乗客（リクエスト）が押し寄せた際、後ろにある複数の「Webサーバー駅（1号店、2号店、3号店）」の混雑状況を見て、「君は1号車ホームへ！君は2号車ホームへ！」と均等に乗り換えるよう振り分ける駅。

### 【ネットワークプロトコル・変換の仕組み】
* **ARP（アープ）** ＝ **「IPアドレスに対応する『固定の駅名（MACアドレス）』を構内アナウンスで探す手続き」**
* **DHCP** ＝ **「駅に到着した乗客（デバイス）に、その駅で使う『IPアドレス』を自動発行・貸出する駅窓口」**
* **NAPT（ナプト / IPマスカレード）** ＝ **ローカル線の「構内IPアドレス」と「全国IPアドレス」を、ポート番号（ホーム番号）を使って束ねて変換する「乗り換え改札の自動変身切符売り場」**
* **HTTP** ＝ **「Web乗客（データ）を運ぶための標準的な電車運行ルール（各駅停車）」**
* **SSL/TLS** ＝ **「乗客（データ）を鍵付きの装甲車に乗せて運ぶ『暗号化運行ルール』」**

### 【DNS（名前解決）関連】
* **DNS** ＝ **「人間の言葉（URL）から駅の『IPアドレス』を調べる案内所システム」**
* **Stub Resolver（スタブリゾルバー）** ＝ **スマホ駅の中にいる「行き方を尋ねる係員（検索依頼係）」**
* **Recursive Resolver（再帰的リゾルバー / フルリゾルバー）** ＝ **街の「中央案内所（あちこちの専門案内所に問い合わせて正確なIPアドレスを調べてきてくれる案内人）」**

## 3. シナリオ別の電車アナロジー解説フロー（追加版）

### A. 【踏み台サーバー（Bastion）】秘密のデータセンター駅へ行く
1. メンテ担当エンジニア駅は、社内の重要データベース駅（超秘密エリア）へ直接向かう線路を持たない。
2. まず、厳重な警備員がいる**踏み台サーバー駅**に到着。
3. そこで厳密な身元確認（SSH鍵認証・多要素認証）をパスして改札を通り、初めて秘密の線路を使って目的地である**データベース駅**へと乗り換える。

### B. 【プロキシサーバー（Proxy）】代理購入駅を経由する
1. スマホ駅は自ら全国ネットに出ず、社内の**プロキシサーバー駅（代理窓口）**へ乗客（リクエスト）を送る。
2. プロキシサーバー駅が「乗客の代わりに全国ネットに出て」目的地サーバー駅へアクセスし、データを取ってくる。
3. プロキシサーバー駅がデータを一時保管（キャッシュ）し、スマホ駅へ手渡す。（外からはプロキシサーバー駅の全国IPアドレスしか見えない）。

### C. 【ロードバランサー（Load Balancer）】混雑を分散する
1. セール開催中、何万人もの乗客（パケット）が `shopping.com` のIPアドレスを目指してやってくる。
2. 全国ネットの出口にある**ロードバランサー駅（振り分け専門駅）**にパケットが次々と到着。
3. ロードバランサー駅が仕分けを行う：「A駅（1号店サーバー）は今空いているからそっちへ！B駅（2号店サーバー）はちょっと混んできたからC駅へ！」と手際よく乗客を分散して乗り換えさせる。
